# 루프 비용 모니터링 대시보드 — 구현 계획서

> **한 줄 요약**: `/loop`로 돌리는 반복 작업(루프) 하나하나가 얼마나 비용(토큰·달러)을 쓰고 있는지,
> 새로고침하면 현황이 보이는 로컬 웹 대시보드를 만든다.
>
> - **작성일**: 2026-08-17
> - **검증 환경**: Claude Code v2.1.232~233, Linux
> - **상태**: 1·2단계 구현 완료 (`tools/loop-dashboard/`, `pnpm loop:dashboard` 로 실행). 3단계는 미착수

---

## 1. 개요 — 무엇을 만드는가

루프 엔지니어링 강의에서 수강생(과 강사)은 한 번에 여러 개의 `/loop`를 띄워놓고 작업시킨다.
이때 "지금 저 루프가 얼마나 돌았지? 토큰을 얼마나 먹지? 비용이 얼마야?"를 알 방법이 터미널 안에는 마땅히 없다.

이 계획서의 목표:

1. **루프별 비용을 자동으로 수집**해서
2. **브라우저에서 새로고침하면 현재 상황이 보이는** 단일 페이지 대시보드를 제공한다.

구성은 아주 단순하게 3개 파트다 (의존성 설치 없이 Node.js 기본 기능만 사용).

```
 ~/.claude/projects/                     ┌─────────────────────┐
 ├─ <프로젝트슬러그>/                     │  수집기 (collect)     │   트랜스크립트 JSONL 읽기
 │   ├─ <세션ID>.jsonl          ────────▶│  · 토큰 4종 합산      │   → 세션(루프)별 집계
 │   │                                  │  · message.id 중복제거│   → 비용 계산
 │   └─ <세션ID>/subagents/*.jsonl       │  · 단가표 적용        │
 │        (서브에이전트 기록)             └──────────┬──────────┘
 │                                                 │
 │                                      ┌──────────▼──────────┐    ┌──────────────────┐
 │                                      │  로컬 서버 (server)   │───▶│  대시보드 (HTML)   │
 │                                      │  GET /api/sessions   │    │  새로고침 = 최신화 │
 │                                      └─────────────────────┘    └──────────────────┘
```

## 2. 배경 지식 — 비개발자를 위한 5분 요약

이 섹션만 읽으면 "무엇을 어떻게 추적하는지"를 이해할 수 있게 쓴다. 수강생 설명용 그대로 쓸 수 있다.

### 2.1 세션 = 대화 기록 파일 하나

Claude Code는 **세션**(한 번 켜고 끄는 대화 단위)마다 **기록 파일을 하나씩** 남긴다.
통화 녹음 파일을 생각하면 된다 — 통화가 끝나도 파일은 남고, 그 파일을 재생(읽기)하면
누가 무엇을 말했는지 전부 다시 볼 수 있다.

- 위치: `~/.claude/projects/<프로젝트슬러그>/<세션ID>.jsonl`
- 파일명이 곧 세션 ID다. (예: `10c6bd5b-4a8f-4bd2-b546-bcb86679056.jsonl`)
- `.jsonl`은 "한 줄이 JSON 하나"인 텍스트 형식. 각 줄이 대화의 이벤트(발언, 도구 사용, …) 하나다.
- 기본적으로 오래된 기록은 약 30일 후 정리된다(`cleanupPeriodDays` 설정으로 조절).

**예시 — 기록 파일의 생김새** (실제 기록에서 모양만 옮기고 값은 간략화했다.
실제 파일에서는 레코드 하나가 한 줄로 쭉 이어진다.)

```jsonl
{"type":"user","sessionId":"926b923f-…","timestamp":"2026-08-17T09:00:00.000Z","message":{"role":"user","content":"지금까지 작업 요약해 줘"}}
{"type":"assistant","sessionId":"926b923f-…","timestamp":"2026-08-17T09:00:04.000Z","message":{"id":"msg_01XYZ…","model":"glm-5.3","usage":{"input_tokens":1204,"output_tokens":536,"cache_creation_input_tokens":8901,"cache_creation":{"ephemeral_5m_input_tokens":8901,"ephemeral_1h_input_tokens":0},"cache_read_input_tokens":45678}}}
{"type":"queue-operation","sessionId":"926b923f-…","timestamp":"2026-08-17T09:05:00.000Z","operation":"enqueue"}
{"type":"ai-title","sessionId":"926b923f-…","aiTitle":"루프 비용 대시보드 조사"}
```

읽는 법:

- **1·2번째 줄** — 사용자 프롬프트와 모델 응답 한 쌍. 응답 줄의 `message.usage`에 토큰 4종이
  기록된다(§2.3 표). `message.id`는 응답 하나하나에 붙는 식별자다.
- **3번째 줄** — 루프(스케줄) 프롬프트가 대화 큐에 들어간 흔적. 이런 줄이 쌓이는 게 곧 반복이다(§2.2).
- **4번째 줄** — 세션에 자동으로 붙은 제목(§3.3).
- 실제 줄에는 이 밖에도 `parentUuid`, `cwd`, `gitBranch`, `version` 같은 메타데이터 필드가 더 있고
  `queue-operation` 줄에는 큐에 들어간 내용이 `content`에 담긴다. 예시에서는 모두 생략했다.

> ⚠️ 이 파일 형식은 공식적으로 "내부 규격, 버전에 따라 바뀔 수 있음"이라고 안내되어 있다.
> 그래서 이 도구는 "버전이 크게 바뀌면 고쳐 쓸 수 있는 단순한 파서"로 만들고,
> 수집 결과를 별도 파일로 저장해 두는 구조(§6)를 택한다.

### 2.2 `/loop`는 세션 하나 안에서 돈다

`/loop`(스케줄 반복 작업)는 **새 세션을 계속 만들지 않는다.** 루프를 건 세션의 대화 큐에
스케줄이 되면 프롬프트가 하나씩 들어가고, 같은 세션에서 이어서 처리된다.

따라서:

> **루프 1개 ≈ 세션 1개 ≈ 기록 파일 1개**

루프 단위 비용 집계 = 세션 단위 비용 집계다. 이것이 이 대시보드의 출발점이다.

- 스케줄 작업은 세션이 꺼지면 함께 정지되고, 반복형은 만들어진 지 7일이 지나면 자동 만료된다.
- 루프가 세션 안에서 발효될 때마다 기록 파일에 `queue-operation`(`enqueue`/`dequeue`) 줄이 남는다.
  → **이 줄의 개수를 세면 "몇 번 반복했는지"를 알 수 있다.**

예외 상황 두 가지는 §8(한계)에서 다룬다: 한 세션에서 서로 다른 루프를 2개 이상 띄우는 경우,
그리고 세션을 재시작하고 다시 `/loop`를 건 경우(새 파일이 생김).

### 2.3 토큰 4종과 비용 — 왜 루프는 돈을 계속 먹는가

API 비용은 "토큰"(텍스트를 셈하는 단위, 대략 단어 조각) 수로 매겨진다. 기록 파일의 각 응답에는
토큰 사용량이 **4가지로 나뉘어** 정확히 기록되어 있다.

| 토큰 종류 | 의미 | 기록 필드명 (`message.usage` 아래) |
|---|---|---|
| 입력 | 이번에 새로 읽은 내용 | `input_tokens` |
| 출력 | 모델이 생성한 내용 | `output_tokens` |
| 캐시 쓰기 | 다음 번 재사용을 위해 저장한 내용 | `cache_creation_input_tokens` (5분/1시간 구분: `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`) |
| 캐시 읽기 | 저장해둔 내용을 다시 읽은 것 | `cache_read_input_tokens` |

**캐시**는 "방금 읽었던 내용을 다시 처음부터 읽지 않게 해두는 장치"다. 읽기(재사용)는
새로 읽는 것보다 **훨씬 싸다**. 공식 단가 규칙(입력 기본 단가 대비 배율):

- 캐시 쓰기(5분짜리) = **1.25배**
- 캐시 쓰기(1시간짜리) = **2배**
- 캐시 읽기 = **0.1배** (10분의 1)

**왜 루프 비용이 누적되는가**: 루프가 발효될 때마다 "지금까지의 대화 전체"를 프롬프트에 실어 보낸다.
세션이 길어질수록 한 번에 보내는 양이 커지고, 앞부분은 캐시 읽기(0.1배)로 싸게 처리되더라도
**횟수 × 컨텍스트 크기**가 곱해지므로 비용이 계속 늘어난다. 그래서 루프 엔지니어링에서는
"반복당 비용이 어떻게 커지는지" 자체를 지표로 봐야 한다 (§4의 M4, M5).

### 2.4 비용은 직접 계산해야 한다

중요한 사실: **이 머신의 기록 파일에는 비용(달러) 값이 기록되어 있지 않다.**
(과거 일부 버전 데이터에는 `costUSD` 필드가 있었으나, 현재 이 머신의 기록 파일에는 없다.)

하지만 **토큰 수는 전부 기록되어 있고** 모델명도 매 응답마다 남으므로,
**"모델별 단가표 × 토큰 수"로 비용을 계산하면 된다.** 계산식은 §5에 정확히 정의한다.

또한 이 머신은 여러 모델(deepseek-v4-flash, glm-5.3, claude-opus-5 등)을 경유해 사용하므로,
단가표는 **사용자가 편집할 수 있는 별도 파일**로 두고, 단가를 모르는 모델은 비용 대신
"단가 미설정"으로 표시한다. (지어낸 단가를 보여주는 일은 없도록 한다.)

## 3. 데이터 소스 — 무엇을 어디에서 얻을 수 있나

수강생에게 "어떤 정보가 남아 있길래 추적이 가능한가"를 설명할 때 쓰는 섹션.
**v1에서 실제로 쓰는 것은 3.1~3.4뿐**이다. 나머지는 존재는 하지만 이번 버전에서 안 쓰는 것들이다.

### 3.1 메인 트랜스크립트 (v1 사용)

`~/.claude/projects/<프로젝트슬러그>/<세션ID>.jsonl` — 세션의 모든 대화 기록.

모델 응답 줄(`type == "assistant"`)에서 다음을 읽는다:

| 정보 | 필드 | 비고 |
|---|---|---|
| 어느 세션인가 | `sessionId` | 전 줄에 공통 존재 |
| 언제인가 | `timestamp` | ISO 8601 |
| 어떤 모델인가 | `message.model` | 단가표 조회 키 |
| 토큰 4종 | `message.usage.*` | §2.3 표 그대로 |
| 응답 식별자 | `message.id` | 중복 제거용 (§5) |
| 서브에이전트 여부 | `isSidechain` | 참고용 |

프로젝트 슬러그는 작업 디렉터리 경로의 비영숫자를 `-`로 바꾼 것이다.
예: `/home/roach/fastcampus-intro` → `-home-roach-fastcampus-intro`.
루프를 다른 디렉터리에서 돌리면 그 디렉터리 슬러그로 파일이 생기므로, 수집기는
**`~/.claude/projects` 전체를 훑고** 대시보드에 프로젝트 컬럼을 보여준다.

### 3.2 서브에이전트 기록 (v1 사용)

루프가 Task(서브에이전트)를 띄우면 그 대화는 **별도 파일**에 남는다:

- 위치: `~/.claude/projects/<슬러그>/<부모세션ID>/subagents/agent-<에이전트ID>.jsonl`
- 안의 줄들은 `isSidechain: true`이며 **`sessionId`는 부모 세션과 같다**.

→ 세션(루프)의 총비용 = 메인 파일 + 같은 세션 디렉터리의 `subagents/*.jsonl` 전부를 합산.

### 3.3 세션 제목 (v1 사용)

기록 안에 `type == "ai-title"` 줄이 있고 `aiTitle` 필드에 사람이 읽는 제목이 들어 있다.
(예: `"Claude Code 비용 모니터링 대시보드 조사"`)
세션 UUID 대신 이 제목을 대시보드 첫 컬럼에 쓴다. 같은 줄이 여러 번 반복 기록될 수 있으므로
마지막 값을 1개만 쓴다.

### 3.4 루프 발효 흔적 (v1 사용)

`type == "queue-operation"`, `operation == "enqueue" | "dequeue"` 줄이 스케줄 작업이
큐에 들어가고 나온 기록이다. **`enqueue` 개수 = 자동 발효 횟수**로 쓴다.

**루프 세션 판별 규칙** (휴리스틱 — 대시보드 설정에서 on/off 가능):

- 그 세션 파일에 `queue-operation` 줄이 하나라도 있거나,
- 사용자 프롬프트 기록에 `/loop` 호출이 보이면
→ "루프 세션"으로 분류한다. 루프가 아닌 일반 세션은 비용이 계산되더라도 기본 필터로 가린다.

### 3.5 이번 버전에서 안 쓰는 것들 (참고용 — 강의에서 "이런 것도 있다"로 소개)

| 무엇 | 어디에 | 왜 v1에서 안 쓰는가 |
|---|---|---|
| statusline 입력 JSON (`cost.total_cost_usd`, `total_duration_ms` 등) | 터미널 상태표시줄 스크립트의 stdin | "지금 화면" 표시용. 파일로 남지 않아 대시보드 소스가 못 됨 |
| hooks (`Stop`, `StopFailure`, `SessionStart`…) | 매 턴 종료 등의 시점에 실행되는 스크립트 | 페이로드에 비용 필드가 없고, 기록 파일은 비동기라 즉시 안 쓰일 수 있음. 3단계 옵션 |
| OpenTelemetry (`claude_code.cost.usage`, `claude_code.token.usage` 메트릭) | OTLP/Prometheus | 공식 실시간 경로이지만 Collector+Grafana 구성이 필요. 수강생 부담 큼. "정석 확장 경로"로만 소개 |
| `ccusage` (커뮤니티 도구) | npm | 검증용으로는 최고 (§7). 커스텀 모델 단가 지정이 필요해 우리 계산기와 병행 |
| 세션 내 `/usage`, `/insights` 명령 | Claude Code 안 | 터미널 안 1회성 조회용. 자동 집계와 무관 |

## 4. 모니터링 지표 — 무엇을 보여줄 것인가

루프 엔지니어링 관점에서 필요한 지표를 먼저 정의하고, 화면은 여기에 맞춘다.
모든 지표는 §3의 데이터만으로 계산 가능하다 (M9 제외, 선택).

| # | 지표 | 정의(계산법) | 왜 보는가 |
|---|---|---|---|
| M1 | **세션(루프) 누적 비용** | §5 공식으로 계산한 합계 | 루프 하나의 총액. 대시보드 기본 정렬 기준 |
| M2 | **발효 횟수 / 반복당 비용** | `enqueue` 수 / M1 ÷ 발효 수(근사) | 루프의 경제성. "한 번에 얼마"가 직관적 |
| M3 | **토큰 4종 합계** | input·output·캐시쓰기·캐시읽기 각각 합 | 비용의 내역. 어떤 토큰이 지배하는지 |
| M4 | **컨텍스트 크기 추이** | 각 응답의 `input + cache_creation + cache_read` 를 시간순으로 | 루프가 길어지며 한 번에 보내는 양이 어떻게 커지는지 (§2.3) |
| M5 | **캐시 읽기 비중** | `cache_read ÷ (input + cache_creation + cache_read)` | 캐시가 잘 먹고 있는지(=돈을 아끼고 있는지)의 핵심 지표 |
| M6 | **모델별 비용 분해** | 모델별로 그룹지어 M1 분해 | 어떤 모델이 비용을 만드는지 |
| M7 | **서브에이전트 비용 비중** | subagents 파일 합계 ÷ M1 | 루프가 서브에이전트를 쓰는지, 얼마나 들이는지 |
| M8 | **활동 기간** | 첫/마지막 `timestamp` | 루프가 언제부터 언제까지 돌았는지 |
| M9 | (선택) 실행 상태 | `claude agents --json` 출력 연동 | 살아있는 루프/끝난 루프 구분. 3단계에서 로컬 출력 확인 후 연동 |

## 5. 비용 계산 규칙 (정확한 정의)

수강생에게 보여주는 숫자이므로, 계산 규칙을 명시적으로 문서로 남긴다.

### 5.1 전처리 규칙

1. **중복 제거 (필수)**: 모델 응답은 스트리밍 과정에서 같은 내용이 여러 줄로 기록될 수 있다
   (예: 35줄 = 실제 응답 14개). **`message.id`가 같은 줄은 마지막 1개만 집계한다.**
   메인 파일과 subagents 파일을 합친 뒤 전역적으로 적용한다(이중 계산 방지).
2. **깨진 줄 무시**: 파일 끝의 아직 덜 쓰인 줄은 JSON 파싱이 실패할 수 있으므로
   줄 단위로 try/catch 하고 실패 줄은 건너뛴다.
3. **토큰 4종은 응답(메시지)별로**, 모델명·타임스탬프와 함께 배열로 보관한다 (M4 시계열용).

### 5.2 계산 공식

모델 \(m\)의 단가 (1M 토큰당 달러, `prices.json`에서 읽음): 입력 \(P_{in}\), 출력 \(P_{out}\).

하나의 응답에 대해:

```
비용 = input_tokens          × P_in  / 1,000,000
     + output_tokens         × P_out / 1,000,000      (thinking 토큰 포함, 출력 단가)
     + ephemeral_5m_tokens   × P_in × 1.25 / 1,000,000
     + ephemeral_1h_tokens   × P_in × 2.0  / 1,000,000
     + cache_read_tokens     × P_in × 0.1  / 1,000,000
```

- 캐시 배율 1.25 / 2.0 / 0.1 은 공식 규격이다.
- 5분/1시간 세부 내역(`cache_creation.ephemeral_*`)이 모두 0인데
  `cache_creation_input_tokens`만 있는 경우: 전체를 5분 쓰기 단가(1.25배)로 계산한다.
  (구버전/일부 경유 응답에서 세부 내역이 비어 있는 경우의 안전한 기본값)

### 5.3 단가표 (`prices.json`)

```jsonc
{
  "krwPerUsd": null,            // 환산률을 직접 입력할 때만 사용 (예: 1380). null이면 USD만 표시
  "models": {
    "claude-opus-5":      { "inputUsdPerMtok": 5,  "outputUsdPerMtok": 25 },
    "claude-sonnet-5":    { "inputUsdPerMtok": 2,  "outputUsdPerMtok": 10 },
    "deepseek-v4-flash":  { "inputUsdPerMtok": null, "outputUsdPerMtok": null }
  }
}
```

- 참고용 기본값: 공식 목록 단가(1M 토큰당) — Fable 5 $10/$50, Opus 5·4.5~4.8 $5/$25,
  Sonnet 5 $2/$10, Haiku 4.5 $1/$5. 작성 시점 기준이므로 파일 주석으로 "공식 요금 페이지에서
  최신값 확인" 안내를 남긴다.
- **단가가 `null`이거나 모델명이 표에 없으면**: 토큰 수는 표시하고 비용은 **"단가 미설정"**으로
  표시한다. 절대 0달러로 보여주지 않는다.
- 이 머신처럼 게이트웨이 경유 모델은 실제 과금이 게이트웨이 단가를 따르므로, 계산값은
  **"추정치"**임을 대시보드 하단에 항상 표기한다.

## 6. 시스템 설계

### 6.1 파일 레이아웃 (이 저장소 내, 웹앱과 무관하게 동작)

```
tools/loop-dashboard/
├── prices.json        # §5.3 단가표 (사용자 편집 대상)
├── collect.mjs        # 수집기: 트랜스크립트 → 세션별 집계 JSON (단독 실행 가능)
├── server.mjs         # 로컬 서버: 요청 시마다 수집 실행 + 대시보드 제공
├── dashboard.html     # 단일 페이지 대시보드 (외부 라이브러리 없음)
└── data/              # (옵션, 3단계) 시점별 스냅숏 저장소
```

Node.js 표준 라이브러리만 사용 (`node:fs`, `node:http`, `node:path`). npm 설치 없음.

### 6.2 수집기 `collect.mjs` 명세

입력: 없음 (고정 경로 `~/.claude/projects` 스캔. `CLAUDE_CONFIG_DIR` 환경변수가 있으면 그 아래
`projects`를 대신 봄). 출력: 아래 JSON (stdout 또는 파일).

```jsonc
{
  "generatedAt": "2026-08-17T12:34:56.789Z",
  "projects": [{
    "slug": "-home-roach-fastcampus-intro",
    "sessions": [{
      "sessionId": "926b923f-…",
      "title": "…",                    // ai-title, 없으면 세션ID 앞 8자리
      "isLoop": true,                   // §3.4 규칙
      "firstSeen": "…", "lastSeen": "…",     // M8
      "firings": 7,                     // enqueue 수 (M2)
      "messages": 23,                   // 중복 제거 후 응답 수
      "tokens": { "input": 0, "output": 0, "cacheWrite5m": 0, "cacheWrite1h": 0, "cacheRead": 0 },  // M3
      "costUsd": 1.23,                  // M1, 단가 미설정 모델 포함 시 null + "unpricedModels": [...]
      "byModel": [ { "model": "glm-5.3", "costUsd": 0.5, "tokens": { … } } ],   // M6
      "subagentCostUsd": 0.2,           // M7
      "perMessage": [ { "ts": "…", "ctxTokens": 45678, "costUsd": 0.03 } ]      // M4 시계열
    }]
  }]
}
```

처리 순서:

1. 프로젝트 디렉터리 목록 순회 → 각 세션 `.jsonl`과 `<세션ID>/subagents/*.jsonl` 나열
2. 줄 단위 파싱 (실패 줄 skip), `message.id` 전역 중복 제거
3. 세션별 토큰 합산 · §5.2 비용 계산 · 지표 계산
4. 루프 판별 · 제목 추출 · 정렬(비용 내림차순)

단독 실행(`node collect.mjs`)하면 표 형태 요약을 콘솔에도 출력한다 (대시보드 없이 터미널에서
확인 가능해야 강의 시연이 쉽다).

### 6.3 서버 `server.mjs` 명세

- `GET /` → `dashboard.html` 반환
- `GET /api/sessions` → **요청 시마다 수집기를 실행**해 최신 JSON 반환 (동일 결과 5초 캐시)
  → "새로고침하면 최신"이 자동으로 성립하고, 별도 수집 데몬이 필요 없다.
- 포트: 3170 (변경 가능). `node server.mjs` 한 줄로 실행.

### 6.4 대시보드 `dashboard.html` 명세

- **상단 요약 타일**: 총 루프 수 · 활성 프로젝트 수 · 합계 비용 · 합계 토큰
- **메인 표** (행 = 세션): 제목 · 프로젝트 · 발효 수 · 응답 수 · 토큰 4종 · 비용 · 기간 · 루프 여부 필터
- **행 클릭 → 상세 패널**: M4(컨퍼텍스트 크기 추이), M2(반복당 비용), M6(모델별 분해), M5(캐시 비중)
- 그래프는 외부 라이브러리 없이 SVG로 그린다.
- 하단 고정 문구: "비용은 단가표 기반 추정치입니다. 단가 미설정 모델은 토큰만 집계됩니다."

## 8. 정확성 주의사항 및 한계 (강의에서 꼭 짚을 것)

1. **비용은 전부 추정치다.** 우리 계산이든 statusline의 `total_cost_usd`든 클라이언트가
   단가표로 계산하는 값이며, 실제 청구와는 다를 수 있다(공식 경고). 게이트웨이 경유 모델은
   실제 과금이 게이트웨이 단가를 따른다.
2. **기록 파일 규격은 비공식이다.** Claude Code 버전 업으로 필드가 바뀔 수 있다(공식 안내).
   수집기가 갑자기 0을 내면 필드 규격 변화를 의심한다.
3. **한 세션에 루프를 2개 띄우면 한 파일에 함께 집계된다.** v1은 세션 단위까지만 지원하고
   발효 단위 분리는 3단계 과제다.
4. **세션 재시작 후 다시 `/loop`를 걸면 새 세션 파일이 생긴다.** 같은 루프라도 세션을
   나눠 돌리면 대시보드에서 여러 행으로 보인다. (자연스러운 동작이지만 강의에서 미리 설명)
5. **기록은 비동기로 쓰인다.** 루프가 막 응답을 끝낸 직후엔 마지막 응답이 아직 파일에
   없을 수 있다. 대시보드는 "직전 상태"까지 보여준다.
6. **오래된 기록은 기본 약 30일 후 정리된다.** 장기 추이는 3단계 스냅숏 저장이 필요하다.
7. **루프는 세션이 꺼지면 정지하고, 반복형은 7일 후 자동 만료된다.** "비용이 안 늘는 루프"는
   죽었을 가능성부터 확인한다.
